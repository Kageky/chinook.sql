# chinook.sql
Анализ продаж Chinook (SQL-only: CTE, подзапросы, оконные функции)
Отдельный SQL-проект на классическом учебном датасете музыкального магазина **Chinook**
(customer, invoice, invoice_line, track, genre, employee — данные о клиентах, счетах, треках
и сотрудниках).
(CTE, подзапросы в FROM/WHERE/HAVING, оконные функции).
Все запросы — в (chinook_analysis.sql).

Бизнес-вопросы
- Какие треки лучше всего продаются внутри каждого жанра?
- Как меняется выручка по месяцам, какой рост month-over-month и накопительный итог?
- Кто из клиентов тратит больше среднего — по отдельным счетам и по среднему чеку?
- Кто из сотрудников приносит больше всего выручки через закреплённых клиентов?
- Кому из клиентов можно предложить конкретный жанр, которого нет в истории покупок?
- Есть ли в базе клиенты вообще без единой покупки?
- Кто из клиентов покупает часто, но по мелочи (кандидат на допродажи)?

Ключевые находки
1. **Топ-3 трека в каждом жанре** — определены оконной функцией `ROW_NUMBER() OVER (PARTITION BY genre)`,
   обёрнутой в подзапрос/CTE.
2. **Только 3 сотрудника реально приносят выручку через клиентов** (Jane — 833.04, Margaret — 775.40,
   Steve — 720.16) — у остальных сотрудников закреплённых клиентов нет.
3. **Сегмент для таргетинга**: 52 из 59 клиентов никогда не покупали жанр Bossa Nova — готовая
   аудитория для рекомендаций/рассылки по этому жанру (для самого популярного жанра, Rock, такой
   сегмент пуст — его покупали все 59 клиентов).
4. **В базе нет клиентов без единой покупки** — проверено антиджойном (LEFT JOIN + IS NULL),
   подтверждает полноту данных.
5. **Обнаружен повторяющийся артефакт тестовых данных**: в нескольких разных месяцах и у разных
   клиентов суммы счетов складываются в одно и то же число (37.62) из одного и того же
   повторяющегося набора сумм — из-за этого рост MoM в некоторых месяцах показывал ровно 0%, а
   "сегмент" частых некрупных клиентов (36 из 59) при проверке оказался тем же артефактом, а не
   реальным различием в поведении. Отличить это от настоящей ошибки в запросе помогла сверка на
   уровне отдельных строк — тот же метод, что и в кейсе с датами в проекте 1.

Реальный кейс по пути
При расчёте выручки по сотрудникам первая версия запроса возвращала пустой результат — джойн
использовал `employee.reports_to` (ID руководителя самого сотрудника) вместо `employee.employee_id`.
После исправления на правильный столбец запрос заработал и показал, что только 3 из всех
сотрудников закреплены за клиентами.
